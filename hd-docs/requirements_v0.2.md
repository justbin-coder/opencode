# 1  项目概述
## 1.1  背景与目的
针对航电软件研发流程中单元测试编写效率低、需求文档结构化程度不足两大核心痛点，本项目旨在构建一套在离线环境下运行的 AI Agent 系统，覆盖「需求理解 → 测试生成 → 执行验证 → 追溯管理」完整链路，大幅提升研发效率与质量可追溯性。
## 1.2  交付范围（优先级分层）
### P0  本期必交（验收基线）

| # | 功能模块 | 核心价值 | 关键指标 |
| --- | --- | --- | --- |
| P0-A | 需求理解与结构化 | 将自然语言需求转换为标准需求卡片（含时序图、验收标准） | 准确率 ≥ 80%，单条 ≤ 30s |
| P0-B | C++ 单元测试自动生成 | 基于源码 + 需求卡片自动生成 CppUnit / gtest 测试代码，覆盖正常 / 边界 / 异常三类场景 | 分支覆盖 ≥ 70%，单函数 ≤ 2min |
| P0-C | 自动编译验证与错误修复 | 生成测试代码后自动调用编译工具，解析错误并循环修复（≤ 3 轮） | 最多 3 轮自动修复 |
| P0-D | 离线部署 | 全栈离线运行，无任何外网依赖（含模型、依赖包、前端资源） | 零外网请求（抓包验证） |
| P0-E | AI Skill 辅助能力 | 将业务约束（编码规范、测试规范等）结构化后自动注入 AI 推理上下文 | Skill 库可配置，注入可验证 |

### P1  二期迭代（范围待定，不计入本期验收）
需求 - 测试 - 代码追溯矩阵（CSV / JSON / Markdown 输出）
需求变更影响分析（受影响代码文件 + 测试用例列表 + 风险报告）
测试执行结果分析与覆盖率缺口识别
回归测试子集智能推荐
Skill 库构建与维护工具

# 2  功能需求详述
## 2.1  P0-A  需求理解与结构化
### 2.1.1  需求卡片输出格式

| 字段名 | 格式 / 示例 | 说明 |
| --- | --- | --- |
| 需求编号 | REQ-2026-03-001 | 系统自动生成 |
| 需求名称 | 飞控数据采集接口 | 不超过 30 字 |
| 提出人 | 张工 | 手动填写或从输入上下文提取 |
| 优先级 | P0 / P1 / P2 / P3 | AI 推荐，人工可修改 |
| 状态 | 草稿 → 已确认 → 开发中 → 已完成 | 初始为"草稿" |
| 功能目标 | 自然语言描述 |  |
| 用户场景 | 角色 / 前置 / 步骤 / 预期结果 | 结构化四要素 |
| 交互流程 | PlantUML 或 Mermaid 时序图 | 格式以项目现有工具为准 ❓ |
| 验收标准 | 可测试的条目列表 | 至少 3 条 |
| 约束条件 | 性能 / 安全 / 合规约束 |  |
| 接口定义 | 函数签名 / API 描述 | 可选，从代码上下文提取 |

### 2.1.2  处理规格
支持批量处理：一次输入 5 ～ 10 条需求
输出格式：Markdown（便于 Git 版本管理）
需求来源：❓ 待确认（详见第 4 章问题 Q3）

## 2.2  P0-B  C++ 单元测试自动生成
### 2.2.1  输入
目标函数 / 类的源码文件
测试框架配置（CppUnit 或 gtest，通过配置文件指定，不硬编码）
关联需求卡片（可选，提供时生成质量更高）

### 2.2.2  输出
完整测试文件（可直接编译），文件名规则：❓ 待确认（详见 Q6）
支持增量生成：在已有测试文件末尾追加新测试用例，不覆盖

### 2.2.3  生成质量要求
覆盖场景：正常路径 + 边界条件 + 异常路径（三类缺一不可）
注释语言：中文（项目合规要求）
Mock 对象：合理使用 Mock，不引入真实硬件依赖
断言：明确断言条件，不允许空断言或 SUCCEED() 占位

## 2.3  P0-C  自动编译验证与错误修复
执行流程如下（最多 3 轮自动修复）：

| 步骤 | 操作 | 负责方 |
| --- | --- | --- |
| 1 | 生成测试代码（P0-B 输出） | AI Agent |
| 2 | 调用编译命令（❓ 待确认具体命令，见 Q5） | AI Agent |
| 3 | 解析编译器错误输出，定位错误行 | AI Agent |
| 4 | 自动修复代码，返回步骤 2（最多循环 3 次） | AI Agent |
| 5a | 编译通过 → 输出测试文件 + 编译日志 | AI Agent |
| 5b | 3 轮后仍失败 → 输出详细错误报告，等待人工介入 | AI Agent |

| ❓ 问题 Q5（见第 4 章） 自动编译修复的边界是什么？仅修复语法 / 链接错误，还是也包括逻辑错误？错误修复失败时的回退机制（保留哪个版本）需明确。 |
| --- |

## 2.4  P0-D  离线部署
AI 推理：使用本地部署的大语言模型（❓ 待确认型号和硬件，见 Q1、Q2）
依赖包：所有 npm / 系统包通过内网 Registry 或 vendor 目录分发
前端资源：所有 JS / CSS / 字体文件本地化，无 CDN 依赖
功能开关：禁用自动更新检查、外部遥测上报
验收标准：在断网环境下抓包，零外网请求

## 2.5  P0-E  AI Skill 辅助能力
AI Skill 是对业务约束（如编码规范、DO-178C 测试规范、项目特有 Mock 模式等）的结构化封装，在生成需求或测试代码时自动注入 AI 推理上下文。

Skill 以 Markdown 文件形式存储，支持人工编辑维护
按场景加载：需求场景加载「需求规范」Skill；测试场景加载「测试规范」Skill
❓ 初始 Skill 内容由谁提供？（见 Q9）

# 4  待客户确认问题清单
以下问题直接影响技术方案选型或工作量估算，建议在下次评审会议中逐一对齐。

| Q1  离线大模型：型号与硬件配置？ 影响：这是整个系统的核心决策，不同模型的推理质量差异极大，硬件要求相差 10 倍以上。 待确认事项： 客户是否已有可用的 GPU 服务器？显存规格是多少（16G / 40G / 80G）？ 无，项目应该包含软硬件 是否有指定模型（如 Qwen2.5-Coder、DeepSeek-Coder）？或由我方推荐？ 无，最先考虑Qwen3.5 30B或更大参数 是否允许使用量化版本（4-bit / 8-bit）以降低显存要求？ INT8可以 |
| --- |

| Q2  服务器操作系统与编译环境？ 影响：直接决定 C++ 编译工具链集成方式（gcc 版本、cmake / make、依赖库）。 待确认事项： 操作系统：Linux（发行版 + 版本）还是 Windows？ Windows gcc 版本？cmake 还是 make？现有构建脚本是什么（能否提供一个示例项目）？ 业务代码项目基于cmake 项目是否已经有可运行的构建脚本（CMakeLists.txt 或 Makefile）？ 有CmakeLists.txt |
| --- |

| Q3  需求的输入来源是什么格式？ 影响：决定是否需要开发文档解析模块（Word / PDF / 纯文本差异很大）。 待确认：需求来源是 Word 文档、纯文本、Excel 表格，还是已有需求管理工具（如 DOORS、Polarion、禅道）？ 先只考虑Markdown格式文本 |
| --- |

| Q4  代码库如何提供给 AI Agent 访问？ 影响：代码索引方式（本地文件系统 / Git 仓库）直接影响上下文检索架构。 待确认：代码库是否托管在内网 Git 服务器（GitLab / Gitee）？AI Agent 是部署在开发者本机还是集中服务器？ 本地文件系统 |
| --- |

| Q5  自动编译修复的能力边界？ 影响：修复范围越广，研发工作量越大，风险也越高。需事先约定边界以避免验收争议。 待确认：自动修复仅限语法错误和链接错误，还是也包括逻辑错误？修复失败后保留哪个版本（原始 / 最后一轮修复版）？ 自动编译修复：仅用于生成的单元测试代码编译错误时，调用工具查看编译器报错原因，修复错误，确保生成代码编译时的正确性 |
| --- |

| Q6  测试框架版本与现有测试文件规范？ 影响：增量生成功能依赖对现有测试文件结构的理解，版本不同代码模板差异较大。 待确认：CppUnit 还是 gtest（或两者都用）？具体版本号？是否有现有测试文件可供参考样本？测试文件命名规则是什么？ 优先支持gtest，有现有的测试文件样板可参考，建议支持学习样板文件，生成编码规则一直的测试代码 |
| --- |

| Q7  用户界面：Web 优先还是必须集成 VSCode？ 影响：VSCode 插件开发工作量约为纯 Web 的 2 倍，且需要单独维护。 待确认：P0 是否必须有 VSCode 插件？还是 Web 界面即可，VSCode 集成作为 P1？ Web即可，CLI也行，当前阶段，不对人机交互太多限制。考虑到演示，尽量能有Web界面即可 |
| --- |

| Q8  航电代码的安全密级要求？ 影响：涉密系统需要额外的审批流程和安全加固措施，可能影响交付周期。 离线部署，物理环境隔绝，不考虑此问题 |
| --- |

| Q9  AI Skill 初始内容由谁提供？ 影响：如需我方整理 Skill 内容，需要客户配合提供编码规范、测试规范等文档，并计入工作量。 待确认：客户是否已有成文的编码规范、测试规范文档（DO-178C 相关）？是否允许我方基于这些文档生成初始 Skill 库？ Skill可由乙方提供模板和通用Skill 甲方自行按照业务编写专用Skill库 |
| --- |

| Q10  同时使用的用户数量？ 影响：单用户本机部署 vs 多用户集中服务部署，架构复杂度差异很大。 待确认：预期同时在线用户数是多少（1～3 人 / 5～10 人 / 20 人以上）？是否需要用户权限管理？ 简化，只考虑单机部署 |
| --- |

# 5  验收标准汇总

| 模块 | 指标 | 验收方法 | 备注 |
| --- | --- | --- | --- |
| P0-A | 准确率 ≥ 80% | 随机抽取 20 条需求，人工评分 | 评分标准待双方确认 |
| P0-A | 单条 ≤ 30s | 计时测试 10 条，取平均值 |  |
| P0-B | 分支覆盖 ≥ 70% | 运行覆盖率工具（gcov / lcov） | ❓ 覆盖率工具待确认 |
| P0-B | 单函数 ≤ 2min | 计时测试 5 个函数，取最大值 |  |
| P0-C | 编译通过率 | 生成 20 个函数的测试，统计首次编译通过率 + 3 轮后通过率 | 通过率目标待确认 |
| P0-D | 零外网请求 | 断网环境下全功能测试，抓包验证 | 硬性要求 |
| P0-E | Skill 注入有效 | 开启 / 关闭 Skill 对比，验证约束是否生效 |  |
